# Kanban Tracker — Kanban Django

## Цель

Создать адаптивное веб-приложение для работы с задачами на канбан-досках с минимальным разграничением прав.

## Технология

Django. Используй Django templates + обычный CSS/JavaScript. Не добавляй React/Vue и другие отдельные frontend-фреймворки.

## Основные экраны

1. Регистрация.
2. Вход.
3. Список доступных досок.
4. Канбан-доска.
5. Создание задачи.
6. Для Менеджера — создание доски и простой экран пользователей/ролей.

## Данные

Пользователь:
- username;
- password;
- role: manager/member.

Доска:
- название;
- дата создания.

Задача:
- название;
- необязательное описание;
- доска;
- статус;
- автор;
- дата создания.

Канбан:
- К выполнению;
- В работе;
- Готово.

## Основной сценарий

регистрация/вход → выбор доски → создание задачи → задача появилась в нужной колонке → допустимое перемещение задачи → после обновления страницы новый статус сохранился.

## Права

Менеджер:
- видит все доски;
- создаёт доски;
- создаёт задачи;
- перемещает любые задачи;
- может менять роль пользователя.

Участник:
- видит доски;
- создаёт задачи;
- может перемещать только задачи, автором которых является сам;
- не может создавать доски;
- не может менять роли.

## Интерфейс

- аккуратный нейтральный светлый интерфейс;
- desktop-first, но без горизонтального выхода элементов на мобильном;
- три визуально различимые канбан-колонки;
- карточки задач;
- понятная индикация текущей роли;
- никаких сложных декоративных эффектов.

## Перемещение задач

Предпочтительно реализовать drag-and-drop.
Если надёжный drag-and-drop заметно усложняет MVP, допустимы явные кнопки/селектор смены статуса.
Главное — изменение статуса должно реально работать и сохраняться в БД.

## Хранение

- локально SQLite;
- подготовь конфигурацию так, чтобы при наличии DATABASE_URL приложение могло использовать PostgreSQL на Railway;
- не усложняй архитектуру.

## НЕ ДЕЛАЕМ В ЭТОМ MVP

- комментарии;
- вложения;
- email;
- Telegram;
- уведомления;
- поиск;
- фильтры;
- дедлайны;
- приоритеты;
- теги;
- аналитику;
- real-time;
- API;
- отдельный SPA frontend;
- тёмную тему;
- сложный профиль;
- сложную админ-панель.

## КРИТЕРИИ ГОТОВНОСТИ

1. Пользователь может зарегистрироваться и войти.
2. Новый пользователь получает роль Участник.
3. Менеджер может создать доску.
4. Пользователь может открыть доску.
5. Пользователь может создать задачу.
6. Задача отображается в правильной колонке.
7. Допустимое перемещение задачи меняет статус.
8. После перезагрузки статус сохраняется.
9. Ограничения ролей реально соблюдаются на backend, а не только скрыты кнопками.
10. Интерфейс не ломается на узком экране.
11. Проект локально запускается штатной Django-командой.
12. Есть requirements.txt.
13. Подготовлена базовая конфигурация для последующего Railway deployment.
